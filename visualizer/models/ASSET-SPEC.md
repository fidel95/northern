# House GLB Asset Specification

For any 3D artist or studio producing a house model for the Northern Pines
visualizer. Anything delivered against this spec drops into
`/visualizer/models/` and works with zero application-code changes. The
current `house-placeholder.glb` in this folder was generated by
`generate-placeholder.py` to this exact spec — open it in Blender as a
structural reference before modeling.

## 1. The core idea

The web app does **not** trust colors/textures baked into the GLB for any
part the customer can customize. It identifies parts by **material name**
and **replaces the material at runtime** with a procedurally- or
texture-driven PBR material chosen from the UI. So:

- Material *names* are a contract. Get them exactly right (case-sensitive).
- Material *appearance* in your DCC tool (Blender/Maya/etc.) only matters
  for your own preview and for parts the app does **not** override (see
  §5, "fixed" materials).
- Geometry, UVs, and object hierarchy are yours to design well — the app
  never touches vertices.

## 2. File format & delivery

- `.glb` (binary glTF 2.0), single file, self-contained.
- One file per house style: `house-modern.glb`, `house-ranch.glb`,
  `house-colonial.glb`, `house-traditional.glb`, etc. Same material-naming
  contract across every file so the same UI drives all of them.
- Geometry compression: **Draco** (`KHR_draco_mesh_compression`) is
  supported by the app's loader and recommended once a hero model exceeds
  ~50k triangles.
- Texture compression: **KTX2 / Basis Universal**
  (`KHR_texture_basisu`) is supported and recommended for production;
  plain PNG/JPG also works and is fine for review builds.
- Both are optional extensions — the loader works with plain, uncompressed
  glTF too, so send an uncompressed review build first and a compressed
  final pass once geometry/materials are signed off.

## 3. Units, orientation, pivot

- **1 unit = 1 meter.** Build at real-world residential scale (an entry
  door is ~2.03 m tall; a single-story eave line is ~2.7–2.9 m).
- **Y-up**, **+Z is the front-facing direction** the default camera looks
  at (i.e. the primary facade / front door faces +Z).
- **Origin at world (0,0,0)**, centered left/right on the front facade's
  midline, sitting exactly at ground level. Include a childless empty
  named `Ground_Anchor` at the true ground-contact point (0,0,0) — the app
  reads its world Y and re-levels the whole model if it's off by a
  fraction, so this is a safety net, not a formality to skip.
- No unapplied transforms on exported meshes (apply scale/rotation in
  Blender before export — `Ctrl+A`).

## 4. Node hierarchy

Exact names below are not required for the app to *run* (it only reads
material names off meshes), but keeping this structure makes the asset
sane to maintain and lets the app do useful things like camera
auto-framing and part visibility toggles later. Match it:

```
House_Root                 (empty, at origin)
├── Body                    (empty) — exterior wall meshes, MAT_Siding
├── Foundation_Group        (empty) — MAT_Foundation
├── Roof                    (empty) — MAT_Roofing
├── Trim                    (empty) — MAT_Trim (fascia, corner boards, casings)
├── Windows                 (empty)
│   ├── Window_Front_01     (empty)
│   │   ├── *_Frame          mesh, MAT_WindowFrame
│   │   └── *_Glass          mesh, MAT_WindowGlass
│   └── … one group per window instance
├── Doors                   (empty)
│   └── Door_Front          (empty)
│       ├── *_Slab           mesh, MAT_DoorSlab
│       ├── *_Glass          mesh, MAT_DoorGlass (lites/sidelights, if any)
│       └── *_Hardware       mesh, MAT_DoorHardware (handle, hinges, kickplate)
└── Ground_Anchor           (empty, no mesh, at 0,0,0)
```

Multiple window/door instances are expected and fine — every instance's
frame mesh uses the same `MAT_WindowFrame` material slot (Blender:
literally the same material datablock, multi-user), same for glass, slab,
etc. The app changes one material and every instance updates at once,
matching the existing "these choices apply to every window on the
elevation" behavior customers already know from the current 2D tool.

## 5. Required material names (case-sensitive)

| Material name       | What it's applied to                          | Runtime-driven by UI? |
|----------------------|------------------------------------------------|------------------------|
| `MAT_Siding`         | Exterior wall cladding                          | Yes — siding type/color |
| `MAT_Roofing`        | Roof shingles/panels                            | Yes — roof color |
| `MAT_Trim`           | Fascia, corner boards, window/door casings, soffit | Yes — trim color |
| `MAT_WindowFrame`    | Window sash/frame                               | Yes — frame color |
| `MAT_WindowGlass`    | Window glazing                                  | Yes — glass type |
| `MAT_DoorSlab`       | Entry/patio door panel face                     | Yes — door color |
| `MAT_DoorGlass`      | Door lites/sidelights glazing                   | Yes — glass type |
| `MAT_DoorHardware`   | Handle, hinges, kickplate                       | Yes — hardware finish |
| `MAT_Foundation`     | Foundation wall / skirting                      | No — fixed, your material renders as-authored |

Anything not in this table (roof flashing, gutters, a chimney, decorative
brackets) is fine to include — give it its own sensibly-named material and
it will simply render with whatever PBR values you author, untouched by
the app, until a future phase wires it up.

### Window styles / grilles

The app does **not** require separate geometry per window *style*
(double-hung vs. casement vs. picture, etc.) in v1 — style differences are
handled procedurally (sash line placement, grille bars) using each window
glass mesh's bounding box. Model one representative, good window
opening per instance; do not model operable sashes or hardware detail
inside the glass — keep the frame simple and let the glass mesh be a
single clean rectangular (or shaped) plane/box, since the app measures it.

If a future phase moves to fully modeled per-style windows, each style
becomes its own optional set of `Frame`/`Glass` meshes swapped in by name
— no material contract changes needed.

## 6. UVs

- One non-overlapping UV set (**UV0**) per material island. Siding, roof,
  and trim should be **real-world-scale UVs** — i.e. a 1×1 m texture tile
  should map to 1×1 m of surface, consistently across the whole model, so
  a tiling texture (lap siding, shingle courses) doesn't stretch or swim
  when swapped at runtime.
- Reserve a second UV channel (**UV1**) for a future baked
  lightmap/AO pass. Not required for v1; nice to have.

## 7. Texture maps (for materials that ship their own textures)

`MAT_Foundation` (and any non-driven decorative material) should ship a
full PBR set if you want it textured rather than flat-shaded:

- **Base Color** (sRGB)
- **Normal** (OpenGL, +Y up — glTF convention)
- **ORM packed**: R=Occlusion, G=Roughness, B=Metallic (single texture,
  glTF's standard packing — do not ship separate O/R/M files)

Resolution targets: 2048×2048 for hero, large-area materials; 1024×1024
for trim/door-scale materials; 512×512 for small hardware. Don't exceed
these — the app runs on phones.

The `MAT_Siding` / `MAT_Roofing` / `MAT_Trim` / `MAT_WindowFrame` /
`MAT_DoorSlab` / `MAT_DoorHardware` materials do **not** need textures
from you at all — the app generates its own procedural PBR maps for every
color/style option and swaps them in. Author them with a plain, roughly
correct base color and mid-range roughness so the model previews sensibly
in Blender/Sketchfab before the web app touches it.

## 8. Poly / file-size budget

- Target **≤120k triangles** total for a hero house model (before any
  Draco compression). This is a phone-friendly ceiling with headroom for
  landscaping/ground added by the app separately — the house itself is
  the single biggest chunk of the frame budget.
- No more than **9 materials of your own** beyond the required list above
  (chimney, shutters, gutters, etc.) — keep draw calls sane.
- Target final `.glb` size **≤8 MB** uncompressed, **≤3 MB** after
  Draco + KTX2. If a single house needs more than that, split
  high-detail-only elements (a chimney with brick normal detail, say)
  into their own optional companion file loaded on demand — talk to dev
  before doing this.

## 9. Delivery checklist

- [ ] File named `house-<style>.glb`, single self-contained binary glTF
- [ ] 1 unit = 1 m, Y-up, +Z front, origin at ground/front-facade midline
- [ ] `Ground_Anchor` empty present at (0,0,0)
- [ ] All 9 required `MAT_*` material names present and applied correctly
      (nothing that should be siding is sitting on the trim material, etc.)
- [ ] Real-world-scale, non-overlapping UV0 on every mesh
- [ ] Triangle count and file size within budget (§8)
- [ ] Opens clean in [gltf-viewer.donmccurdy.com](https://gltf-viewer.donmccurdy.com/)
      or Blender's glTF importer with no console errors
- [ ] Sanity-checked against `house-placeholder.glb` for scale (import
      both into the same Blender scene — proportions should be close)
